# Rendering strategies: the lesson

This file maps every rendering strategy in Next.js 16.4 and React 19.3 to the
Dudesphere route and story that teaches it. Each web story adds or updates its
row. The `/lab` page (WEB-11) lists every row of the Routes table, for admins.

WEB-11 checked `ensureStatic`, `use(browser())`, `catchError`, `refresh()` and
`instant()` against the installed Next 16.4 docs, and the rows below name them
as confirmed. If a later story finds that an API works differently, it fixes the
row.

## What a rendering strategy is, with Cache Components on

A rendering strategy decides when a page's HTML is made and how long it is kept:
at build, at request, or from a cache in between.

Dudesphere turns on `cacheComponents: true` in `apps/web/next.config.ts`. That
changes the model in three ways.

1. **Dynamic by default.** Nothing is cached unless the code asks. A page that
   reads data reads it fresh on every request.
2. **Opt into caching with `'use cache'`.** A page, a component or a function
   marked `'use cache'` keeps its output. `cacheLife()` says how long.
   `cacheTag()` names the entry so a write can expire it.
3. **A static shell with streamed holes.** At build, Next prerenders everything
   that does not read request data into a static shell, cached parts included.
   Each `<Suspense>` boundary around request data, such as `cookies()`, becomes a
   hole. The shell is sent at once, and each hole streams in when its data
   resolves. This model replaced the `experimental.ppr` flag of Next 14 and 15.

A read of request data outside `<Suspense>` is a build error, not a slow page.
That rule shapes every page below.

## Routes

One row for each route and strategy. A route that teaches several strategies has
a row under each. The Route column holds a URL path, or a file path when the
strategy has no route of its own. A file path uses one of two roots: `proxy.ts`,
`lib/api.ts`, `app/...` and `components/...` are under `apps/web/src`, and
`next.config.ts` and `e2e/*.spec.ts` are under `apps/web`.
The names in the Strategy column match the first column of the table above.
Status is Built when the route, file or setting exists in the code, and Planned
when its story is not built yet. `apps/web/src/content/lab.ts` holds the same rows,
and `lab.spec.ts` fails when the two copies differ.

## Known limit: JavaScript-off Server Action errors

With `cacheComponents` on, Next 16.4 (seen on 16.4.0 and 16.4.1) answers a JavaScript-off Server Action
POST that does not redirect with flight data only, and no HTML shell. The
browser shows a blank page. Next.js tracks it as [vercel/next.js#99756](https://github.com/vercel/next.js/issues/99756), and the fix is in review as [#99981](https://github.com/vercel/next.js/pull/99981).

AUTH-7 found this in its Task 1 spike. The effect on the sign-in and sign-up
forms:

- **Success works.** `redirect()` sends a 303, and the browser follows it to `/`
  or to a safe `next`. With JavaScript off there is no `next`, so it lands on
  `/`.
- **An error shows a blank page.** Wrong credentials, a taken name, a rate limit
  and a server error all return state instead of redirecting, so each one is
  blank with JavaScript off. With JavaScript on, the errors show under the
  inputs as designed.
- **The forms catch the common mistakes in the browser first.** `required`,
  `type="email"`, `minlength`, `maxlength` and a username `pattern` copy Nest's
  DTO rules, so a JavaScript-off visitor rarely posts a value that Nest would
  refuse with a 400. Nest still decides.
- **One test pins the blank page.** `e2e/auth.spec.ts` checks the
  JavaScript-off success path and adds one test that records the blank-error
  behaviour, so a Next fix shows up as a failing test.

AUTH-9 has the same limit. Forgot redirects on success, so forgot works with
JavaScript off: it lands on `/forgot-password/sent`. Its errors return state, so
they still show a blank page with JavaScript off. The same limit holds for any
later form that returns state.

## Known limit: a form in a Suspense hole never shows with JavaScript off

This one is not a Next bug. It is how React's streaming renderer sends a `<Suspense>`
hole. Cache Components only forces the `searchParams` read into a hole. Next sends the hole's content inside `<div hidden id="S:n">`, and only
React's inline script moves it into place. With JavaScript off, the script never
runs, so the content stays hidden and the visitor sees only the fallback in the
static shell.

AUTH-9 accepted this for the reset page:

- **The reset form never shows with JavaScript off.** It reads `?token=`, so it
  must sit in a hole (`ResetPasswordFromLink`). The hole's fallback is in the
  static shell and holds a `<noscript>` line: "Turn on JavaScript to set a new
  password." So a JavaScript-off visitor is told what to do, and the reset
  itself needs JavaScript.
- **The `/login?reset=1` notice is hidden the same way.** That is harmless: the
  sign-in form is in the static shell and still works.
- **After a reset, the notice takes focus.** The redirect leaves focus on the page
  body, and a live region that arrives already filled is often not announced, so
  `FocusedNotice` focuses the `<output>` on mount (`tabIndex={-1}`), but only when nothing else has
  focus, so a member already typing in the sign-in form is not interrupted.
- **Forgot is not affected.** Its form is in the static shell, and success is a
  303 to `/forgot-password/sent`.

The rule that follows: a form that must work with JavaScript off belongs in the
static shell, never in a hole.

## The `/lab` page

`app/(app)/lab/page.tsx` is the index of this lesson, built in WEB-11. It is for
admins only. It lists every strategy in the table above as a heading with its
meaning, and under each heading the rows of the Routes table. A built page row
links to the live route. A planned row shows its story id and no link. Handlers
and files have no link either.

The page itself is synchronous, and only its heading is in the static shell. The
rows sit in one `<Suspense>` hole that calls `requireAdmin("/lab")` first, so
the rows never reach a visitor who is not an admin. No session redirects to
`/login?next=/lab`. A signed-in member who is not an admin gets the "There are
rules" page, through `forbidden()`. The status stays 200, not 403, because the
call runs inside `<Suspense>` after streaming starts. Next renders
`forbidden.tsx` in place of the page's content (the heading, the intro and the
hole) and adds a `noindex` tag. The role comes from Nest
through `getMe()`, never from the token.

A member keeps the "Rendering lab" tab title, even though the page shows "Off
limits". The title is in the shell that is sent before the role check runs, and
that is part of the lesson.

The rows come from `apps/web/src/content/lab.ts`, not from this file.
`lab.spec.ts` reads this file and fails when the two copies differ, so a row
cannot be added to one and forgotten in the other.

## How to record a new use

Every web story with the `rendering-lesson` label does this before it is Done:

1. Find the strategy's row in the table above. Add the route and the story id to
   "Where Dudesphere uses it". If the strategy is new, add a row.
2. Fill the `## Rendering strategy` section of `issues/<ID>.md` with the same
   facts.
3. Add one row to the Routes table above and the same row to
   `apps/web/src/content/lab.ts`. `/lab` shows it from `lab.ts`. Run
   `pnpm --filter @dudesphere/web test` and `lab.spec.ts` tells you if the two
   copies differ. Set `href` only on a built page a visitor can open.
4. If the story found that an API works differently from its row, fix the row.
