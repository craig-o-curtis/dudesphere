# AUTH-9: Forgot and reset password pages

- **Issue:** #43
- **Spec:** [issues/AUTH-9.md](../issues/AUTH-9.md)
- **Branch:** `43-auth-9-forgot-and-reset-password-pages`. It doesn't match `feature/<id>-<slug>`, because `worktree branch --github` named it. Not renamed.
- **Blocked by:** AUTH-7 (✅ Done, PR #91). AUTH-8 (✅ Done, PR #93) and WEB-54 (✅ Done, PR #92) also merged first. All three are on `main`.
- **Status:** Finalizing

## Scope

A member who forgets their password asks for a link on `/forgot-password`. Nest emails it, and the page always sends them on to `/forgot-password/sent`, whether or not the address has an account. The link opens `/reset-password`, where they set a new password twice. This ends every sign-in and sends them to `/login?reset=1` to sign in again. `/login` gets a "Forgot password?" link, and every auth form gets a visible "All fields are required." line.

There's no API change, no migration and no new e2e table. Both Nest routes exist in `apps/api/src/auth/password-reset.controller.ts`, and reset tokens live in `email_tokens`, which `E2E_TARGETS` already covers.

## Decisions

Two rounds, 2026-10-15. The user accepted the recommendation every time except round 2, question 4.

Round 1:

- **Forgot-password success: redirect to a static `/forgot-password/sent`.** With JavaScript off, a Server Action that returns state shows a blank page (#99756), so a success message returned as state would be blank. On 202, `requestReset` redirects with a 303. `/sent` says "If that address has an account, we sent it a link." Errors (400, 429 with `Retry-After`, Nest down) still return state, as sign-in does.
- **`FRONTEND_URL`: no env change.** Nest already defaults it to `http://localhost:3001`, and `''` falls back to that default (`apps/api/src/config/env.validate.ts:184`). `.env.example` and Craig's `.env` stay as they are, and the spec's Gap, Scope and Done when get corrected.
- **The match check runs in `resetPassword` only.** On a mismatch it returns "The two passwords don't match." under "Same again" and makes no Nest call. There's no check in the browser.
- **`AuthForm` becomes a plain shell.** `NextPathField`, its `<Suspense>`, `carryNextPath` and `CookieNote` move into `SignInForm` and `SignUpForm`, which behave exactly as before. Forgot and reset don't carry `next` or show the cookie note. So `/forgot-password` has no Suspense hole.

Round 2:

- **Full-flow Playwright spec through Mailpit.** `e2e/password-reset.spec.ts` reads Mailpit's HTTP API on 8025 through a small helper. It skips when Mailpit is down, and deletes its `e2e-` messages afterwards. The hand check still happens.
- **One "That link no longer works." state.** It covers a URL with no token (no form is rendered), a 400 whose messages are about `token`, and `RESET_TOKEN_INVALID`. It links to `/forgot-password`.
- **"Forgot password?" sits under the password field** on `/login`, as an `InlineLink`, before Sign in.
- **Strip the token on load.** The user chose this over the recommendation to leave it. A small client component calls `window.history.replaceState` to `/reset-password` once the hidden token input has rendered. A reload afterwards shows "That link no longer works.", and that is accepted.

Kept from the spec: a `Referrer-Policy` header on `/reset-password`, set in `next.config.ts` `headers()`. It is `strict-origin`, not the spec's `no-referrer`, after fix round 1 (see the Log). `clearSessionCookies()` runs before the redirect to `/login?reset=1`, and `/login` then shows "Password changed. Roll in with the new one." The password inputs take `minLength` and `maxLength` from `lib/auth-rules.ts` (12 and 128). No page calls `getMe()`.

## PR

**Title:** AUTH-9 (#43): Forgot and reset password pages

**Body:**

## What a member can now do

A member who forgot their password asks for a link on `/forgot-password`. The page always sends them on to `/forgot-password/sent`, whether or not the address has an account. The emailed link opens `/reset-password`, where they set a new password twice. That ends every sign-in and sends them to `/login?reset=1`, which says "Password changed. Roll in with the new one." `/login` has a "Forgot password?" link under the password field. Every auth form shows an "All fields are required." line (fixes WEB-54's A11Y-1).

## What changed

Web app only. There is no API change, no migration and no new e2e table. Both Nest routes and the reset tokens already existed.

- `AuthForm` is now a plain shell. The next-path field and cookie note moved into `SignInForm` and `SignUpForm`, which behave as before.
- New `requestReset` and `resetPassword` Server Actions. A password mismatch is caught before any call to Nest. Bad tokens all show one "That link no longer works." state. On success the action ends this browser's old sign-in at Nest, clears the cookies and redirects.
- `apiFetch` returns `undefined` for an empty 202 or 204 body. An empty 200 or 201 still throws.
- `proxy.ts` lets the three password pages through untouched, so a refresh redirect can't carry the reset token into `/login?next=`.
- The reset page sends `Referrer-Policy: strict-origin`. The reset form strips the token from the address bar once it has rendered.
- New browser test `password-reset.spec.ts` runs the whole flow through Mailpit.

## Rendering strategy

Every new page is ◐ (partial prerender). The forgot form is in the static shell. The reset form reads `?token=`, so it sits in a `<Suspense>` hole. Details are in `rendering-strategies.md`.

## What the story teaches

[Rendering lesson, AUTH-9 entry](lessons/rendering-lesson.md#auth-9-forgot-and-reset-password-pages): a form that needs a value from the URL before it can render must sit in a `<Suspense>` hole, and a hole shows only after React's inline script swaps it in. So the reset form needs JavaScript, and its fallback says so in a `<noscript>` line. The forgot form reads nothing from the request, so it stays in the shell and works with JavaScript off.

## Accepted limits

- **JavaScript off.** The reset form does not show. Its fallback says "Turn on JavaScript to set a new password." Errors from a Server Action show a blank page (vercel/next.js#99756). Forgot succeeds, because it redirects.
- **The token stays in `history.state`.** After the strip, Next's router tree for that entry still holds it. Only a script on that page can read it, the token works once, and it expires after 30 minutes.
- **Expired access token at reset.** If this browser's access token has expired but its refresh token is live, the sign-out gets a 401. That sign-in lives at Nest until it expires, with its only cookie cleared. This is like AUTH-8's QA-4.
- **Shared rate-limit bucket.** Until API-10 (#44), every web visitor shares one IP, so one visitor can use up a member's 3 forgot tries.
