# AUTH-7: BFF sign-up, sign-in and sign-out with httpOnly cookies

- **Issue:** #41
- **Spec:** [issues/AUTH-7.md](../issues/AUTH-7.md)
- **Branch:** `41-auth-7-bff-sign-up-sign-in-and-sign-out-with`. It doesn't match `feature/<id>-<slug>`, because `worktree branch --github` named it. Not renamed.
- **Blocked by:** none in tracker.md. The spec names WEB-5, WEB-6 and REPO-3. All three are Done, and WEB-6 is on `main` (`efd0874`, PR #88).
- **Status:** Done

## Scope

A visitor can sign up and sign in from `/signup` and `/login`, with JavaScript on or off. Next keeps Nest's token pair in two httpOnly cookies, and page scripts never see a token. A signed-in member sees a corner on `/` with "Sign out" and "Sign out everywhere". Both end the sign-in in Nest at once, and the access tokens stop working. The browser never calls Nest.

## Decisions

Round 1 (2026-10-14):

- **Sign out.** It can't be a Server Action. An action posts to the page's own path, so the `refresh` cookie, limited to `/api/auth`, never reaches it (Next docs `server-actions.md:78`). Two plain `<form method="post">` buttons post to Route Handlers:
  - `api/auth/logout` calls `POST /auth/token/revoke` with the refresh token.
  - `api/auth/logout-everywhere` calls `POST /auth/sign-out-everywhere` with the access token. If the access token is missing, or Nest answers 401, it first swaps the refresh token through `POST /auth/token/refresh` and tries once more.
  - Each calls `assertSameOrigin()`, clears both cookies (refresh at its own path) and answers 303 to `/`.
  - The spec's `signOut()` and `signOutEverywhere()` actions are dropped.
  - The cookie paths stay. A refresh cookie at `/` would travel on every request, and proxy's parallel requests could race a single-use token.
- **proxy.ts.** None in AUTH-7. AUTH-8 builds it, for optimistic redirects only. Each `/api/auth` handler checks Origin itself through a shared `assertSameOrigin()`. The Next docs warn that a matcher change can silently drop proxy coverage (`proxy.md:249-251`). Fixed security headers go to WEB-45, in `next.config.ts` `headers()`.
- **400 messages.** Nest sends a flat array. `lib/api.ts` maps each message to a field by its leading property path: `username`, `email`, `password`, `identifier`, and `profile.displayName` becomes `displayName`. Any other message becomes a form-level error. A Vitest table pins the real DTO messages. The actions return `{ fieldErrors, formError, values }`. `values` never holds a password.
- **Signed-in UI.** A corner on `/` sits inside `<Suspense>` and reads the cookies. Sign-in and sign-up land on `/`, or on `next`. `/login` and `/signup` always show their forms, with no bounce. A `session` cookie can look alive for up to 15 minutes after Nest ended the sign-in, and a bounce would lock that member out.

Round 2:

- **JavaScript off.** A spike proves it first. Then `e2e/auth.spec.ts` runs against the real API, locally, in WEB-6's Playwright setup. CI waits for WEB-46. Forms sit in the static shell, never inside a Suspense hole, because a hole shows only its fallback with JavaScript off. A signed-in visitor with JavaScript off sees the signed-out fallback on `/`. This is accepted, and FEED-12 owns the corner later.
- **One server-only `lib/session.ts`.** It holds the cookie names, options and lifetimes, `startSession`, `clearSessionCookies` and `readSessionCookies`. It replaces the spec's `lib/auth-cookies.ts`. AUTH-8 adds `verifySession`, `getMe` and `requireSession` to it.
- **`?next=` now.** `safeNextPath()` lives in `lib/next-path.ts`. A small client component, `NextPathField`, reads `useSearchParams()` inside its own `<Suspense fallback={null}>` and writes a hidden `next` input. With JavaScript off there is no `next`, and sign-in lands on `/`.

Round 3:

- **Sign-in shape.** Password sign-in and sign-up are Server Actions. `startSession(pair, next)` in `lib/session.ts` finishes every sign-in: it sets both cookies and returns the safe target. AUTH-52's email-link, passkey and Google and GitHub handlers will call it too. There are no `api/auth/login` or `api/auth/signup` handlers, because nothing calls them, now or in AUTH-52.
- **Email only.** The login field is "Email", `type="email"`, `autocomplete="username"`, still posted to Nest as `identifier`. Sign-up keeps its username field, because Nest requires one, with a "private" hint. AUTH-52 decides whether usernames go for good.
- **Cookies and privacy.** No banner. The session, refresh and theme cookies are strictly necessary or set at the member's request, so they need no consent. One plain cookie line sits under both forms. A new story, WEB-53 "Privacy and cookies page", holds the GDPR Art. 13 notice and blocks WEB-45. Any later analytics or third-party embed reopens the consent question.
- **API-10 headers.** Left to API-10. `apiFetch` takes an optional `extraHeaders` argument, so API-10 adds `X-Bff-Secret` and `X-Client-Ip` there.

Round 4 (accepted):

- **Half-finished sign-up.** `signUp` stays on `/signup` and returns "Your account is ready, but we couldn't sign you in just now." with a "Sign in" link to `/login` that carries `next`.
- **Cookie names and flags.** `__Host-session` (`path=/`, `maxAge` = `expiresIn`) and `__Secure-refresh` (`path=/api/auth`, `maxAge` 604800). Both are `httpOnly`, `secure: true` always, and `sameSite: "lax"`.
- **Clearing.** Both cookies are cleared with `set(name, "", { path, maxAge: 0 })`, never `delete(name)`, which only clears `/`. Use `maxAge`, never `expires`, which takes a `Date`.
- **Native `required`** on every input.
- **"Forgot password?"** waits for AUTH-9.
- **The AUTH-8 prefetch fix:** the matcher's `missing` rule plus `Sec-Fetch-Dest: document`.
- **The copy** is as drafted. See Tasks 7, 8 and 9.
- **WEB-53** is filed as [#89](https://github.com/craig-o-curtis/dudesphere/issues/89).

Round 5, after the Task 1 spike (2026-10-14):

- **A JavaScript-off error shows a blank page.** With `cacheComponents` on, Next 16.4 answers a JavaScript-off POST that does not redirect with only its flight data and no HTML shell. The success path's 303 works. The user chose to accept the gap and harden the forms in the browser:
  - Tasks 7 and 8 add native constraint attributes that copy Nest's DTO rules: `required`, `type="email"`, `minlength` and `maxlength`, and a `pattern` for the username (no `@` or spaces). Read the rules from `apps/api/src/auth` and the users DTOs; don't guess.
  - With JavaScript off, wrong credentials, taken names, rate limits and server errors still show a blank page. This is written down in the spec and in `rendering-strategies.md` as a known Next limit.
  - Task 10 tests the JavaScript-off success path only, plus one test that pins the blank-error behaviour, so a Next fix shows up.
  - The bug was already filed as [vercel/next.js#99756](https://github.com/vercel/next.js/issues/99756), with a fix PR, [#99981](https://github.com/vercel/next.js/pull/99981), in review. We added a comment with a smaller repro.

## PR

**Title:** AUTH-7 (#41): BFF sign-up, sign-in and sign-out with httpOnly cookies

**Labels:** epic-lebowski, enhancement, rendering-lesson, auth-lesson, fullstack. **Milestone:** Phase 0: Foundation.

## What a member can now do

- Sign up at `/signup` and sign in at `/login`, with JavaScript on or off.
- Land on `/`, or on a safe `?next=` path after signing in.
- See a corner on `/` with "Sign out" and "Sign out everywhere" once signed in.
- Signing in again ends the member's previous sign-in at Nest.

The browser never calls Nest and never sees a token. Next keeps Nest's token pair in two httpOnly cookies: `__Host-session` (path `/`, 900 seconds) and `__Secure-refresh` (path `/api/auth`, 604800 seconds). Both are `Secure` and `SameSite=Lax`.

## What changed

**apps/api**

- New route `POST /auth/sign-out` (bearer, 204). It ends the access token's own sign-in by `sid`, through a new `SignInsRepository.endSignIn`. It cannot end another member's sign-in.
- Documented in `context/overview.md`, `README.md`, `DEVELOPMENT.md` and `reference/TOKENS_AND_SESSIONS.md`.
- No migration and no new table.

**apps/web**

- `lib/api.ts` (server-only `apiFetch`, `ApiRequestError`, mapping of Nest's 400 messages to fields), `lib/session.ts` (cookies, `startSession`, `clearSessionCookies`, `readSessionCookies`), `lib/next-path.ts` (`safeNextPath`), `lib/origin.ts` (`assertSameOrigin`) and `lib/route-responses.ts`.
- Server Actions `signIn` and `signUp` in `lib/actions/auth.ts`.
- Route Handlers `POST /api/auth/logout` and `POST /api/auth/logout-everywhere`. Sign-out cannot be a Server Action, because the refresh cookie only travels to `/api/auth`. Each handler checks Origin itself and answers 303 to `/`.
- Pages `/login` and `/signup`, the forms, `NextPathField`, `CookieNote`, `SessionCorner` and the `useFocusFirstInvalid` hook. Focus moves to the first invalid field after a failed submit.
- `next.config.ts` sends `frame-ancestors 'none'` and `X-Frame-Options: DENY` on every route.
- Browser tests in `e2e/auth.spec.ts`, and an updated tab-order test in `e2e/shell.spec.ts`.
- Docs and specs: `rendering-strategies.md`, `frontend-architecture.md`, the AUTH-8, AUTH-9, AUTH-52, API-10 and WEB-45 specs, and a new WEB-53 spec (Privacy and cookies page, #89).

## Rendering strategy

`/login` and `/signup` are static shells (`◐`) with the form in the shell, so it works with JavaScript off. `NextPathField` reads `?next=` in its own `<Suspense fallback={null}>`. `/` is a static shell with a streaming hole for `SessionCorner`, which reads the cookies. Sign-in and sign-up are Server Actions using `useActionState`, and success is a 303 redirect.

## What the story teaches

- Rendering: A page stays static when only its request-time reads go into small `<Suspense>` holes, and a form stays in the shell so it works with JavaScript off. See [lessons/rendering-lesson.md](lessons/rendering-lesson.md#auth-7-bff-sign-up-sign-in-and-sign-out-with-httponly-cookies).
- Auth: Next is the BFF. It keeps both tokens in httpOnly cookies, sign-in can be a Server Action, and sign-out must be a Route Handler that checks Origin itself. See [lessons/auth-lesson.md](lessons/auth-lesson.md#auth-7-bff-sign-up-sign-in-and-sign-out-with-httponly-cookies).
