## Scope

A member stays signed in past the 15-minute access token. When the token is about to run out, a full page load or a client-side navigation goes through `/api/auth/refresh` and comes straight back, signed in. Anonymous visitors are never redirected. Every page asks "who is signed in" through one cached, server-only Data Access Layer in `lib/session.ts`. Client components call Nest through an allow-listed `/api/bff/*` proxy, and `clientFetch` refreshes once on a 401.

## Decisions

Round 1 (2026-10-15):

- **No redirect loop: a 7-day session cookie.** Proxy can't see the refresh cookie (path `/api/auth`). Under the spec's "missing cookie means refresh" rule, an anonymous visitor would loop: refresh, then `/login`, then refresh again. So `__Host-session` now lives as long as the refresh cookie (`REFRESH_MAX_AGE_SECONDS`, 7 days), not `expiresIn`. Proxy refreshes only when the cookie is there and its `exp` is within 60 seconds, or can't be read. No cookie means anonymous, and the request passes through. Every refresh failure clears `__Host-session`, so nothing can loop. `verifySession` treats an expired token as null. SessionCorner switches to `verifySession`. No third cookie, so the CookieNote copy ("sets two cookies") stays true.
- **Any navigation refreshes, after a spike.** A client-side `<Link>` click is an RSC fetch with `Sec-Fetch-Dest: empty`, so the spec's document-only rule would send members to `/login` 15 minutes into a visit. The Next docs strip RSC headers in proxy on purpose, so that RSC and HTML requests are treated the same (`proxy.md`, "RSC requests and rewrites"). Proxy redirects every GET that reaches it. The matcher's `missing` rule keeps prefetches out, and Server Action POSTs pass through. Task 1 proves this first. **Fallback** if the spike fails: keep the document-only rule, and `requireSession` redirects to `/api/auth/refresh?next=` instead of `/login`.
- **Reuse race: keep the result 10 seconds.** Nest revokes the whole sign-in when a refresh token is used twice, and has no grace period (`@nestjs/authentication` `token.service.js:134-149`). If the entry were deleted on settle, a second tab arriving a few milliseconds late with the old cookie would sign both tabs out. The settled pair stays in the Map for 10 seconds (`setTimeout`). Failures are dropped at once. Accepted cost: a thief who replays the old token on the same instance within those 10 seconds gets the new pair.
- **Nest down: clear the session cookie only.** On a 5xx, a 429 or no answer, the handler logs with `logFailure`, clears `__Host-session`, keeps `__Secure-refresh` (still unspent) and answers 303 to `next`. The page renders signed out, or `requireSession` sends to `/login`. `POST` answers 503, and `clientFetch` then hands its caller the original 401, with no redirect.

Round 2:

- **Placeholder `/feed`.** FEED-13 builds `/feed` and waits on AUTH-8. AUTH-8 builds a minimal `(app)/feed/page.tsx`, so the `/feed` fallback lands somewhere real. It also gives `requireSession` and `getMe` a page to prove themselves on. FEED-13 replaces its body.
- **`X-Bff-Secret` and `X-Client-Ip` go to API-10.** Nest reads neither yet (API-10, #44, Todo). The BFF route sends the bearer only. API-10's spec gains a line: the headers go on every BFF call, `/api/bff` included, from one helper.
- **BFF guards, all four:**
  - The allow-list is `abidings`, `hashtags`, `profiles` and `users/me`, matched segment by segment. `lanes` waits for LANE-25 (#60), the first story whose client polls `/lanes/games`.
  - `assertSameOrigin()` on POST, PATCH and DELETE (403).
  - `.` and `..` segments, empty segments, encoded slashes and backslashes answer 404 before the allow-list check.
  - Only the method, the query string, `Content-Type` and the body go to Nest. Only the status, `Content-Type`, `Retry-After` and the body come back.
- **Labels.** Add `auth-lesson` to #42, so the mentor writes an auth lesson as well as the rendering lesson.

## Verification

- With `JWT_EXPIRES_IN=60` in `apps/api/.env` (it must be 3 or more), sign in, wait 61 seconds, open `/feed`: the network panel shows one redirect through `/api/auth/refresh`, and the page renders signed in.
- The same after a client-side `<Link>` navigation (per Task 1).
- An anonymous visitor on `/`, `/login` or `/feed` never goes through `/api/auth/refresh`. `/feed` sends them to `/login?next=%2Ffeed`.
- Two tabs reload at the same moment after expiry: Nest sees one refresh call per instance, and both tabs stay signed in. The same with the second tab a moment later, within 10 seconds.
- Replay an old refresh token by hand: Nest answers "reused", both cookies are cleared, and the browser lands on `/login?next=`.
- With Nest stopped, an expired session renders the page signed out, and `__Secure-refresh` survives.
- A hovered link prefetch with a dead session makes no refresh call, and never reaches `proxy.ts`. A document request does.
- `next=https://evil.example.com` on the refresh handler redirects to `/feed`, and so does a request with no `next`.
- Signing in again after the access token expired ends the previous sign-in at Nest: its tokens get 401.
- Importing `lib/session.ts` from a Client Component fails the build.
- `GET /api/bff/users/1` (outside the allow-list) answers 404. A cross-origin `POST /api/bff/abidings` answers 403.
- A page that calls `getMe()` three times makes one Nest call (API log count).
- `rendering-strategies.md` has the AUTH-8 lines.
- These all pass: `pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm build`, `pnpm --filter @dudesphere/web test`, `pnpm --filter @dudesphere/web test:e2e` (with the API up) and `pnpm e2e:check`.
